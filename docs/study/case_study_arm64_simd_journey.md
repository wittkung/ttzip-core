## 1. 案例背景与问题定义

在无损压缩算法（如 Deflate / RFC 1951）中，**最长匹配搜索（Longest Match Search）** 是占据整个 CPU 压缩耗时 50%~70% 的绝对核心热点。在 `zlib-ng` 中，该热点被抽象为 `compare256(src0, src1)` 函数——计算两个字节流从当前指针开始的最长连续相同字节数（最大 256 字节）。

在 2022 年，`zlib-ng` 维护者 Nathan Moinvaziri 设计了一个经典的 16 字节单循环实现：
```c
// 原始 Baseline: 16 字节后变址加载与双车道标量提取
LOAD_16B_PAIR(a0, b0, src0, src1, offset);
cmp0 = veorq_u8(a0, b0);
lane0 = vgetq_lane_u64(vreinterpretq_u64_u8(cmp0), 0);
if (lane0) return len + zng_first_diff_byte64(lane0);
lane1 = vgetq_lane_u64(vreinterpretq_u64_u8(cmp0), 1);
if (lane1) return len + 8 + zng_first_diff_byte64(lane1);
```

### 问题提问：
在现代 AArch64 处理器（如 Apple Silicon M 系列或 ARM Neoverse）上，这个看似完美的 16 字节单循环存在什么潜在瓶颈？我们能否直接用 32 字节双展开 + `vmaxvq_u8` 横向规约来加速它？

### 阶段 1：朴素直觉与局部跑分假象
- **直觉思维**：“既然 NEON 寄存器是 128 位的，循环每次处理 16 字节太慢了，直接每轮加载两个 128 位（32 字节），用 `vorrq_u8` 把差异合并，最后用一条 `vmaxvq_u8` 判定是否全等！”
- **局部微观跑分**：在 256 字节满匹配（Full Match）测试下，耗时直接从 6.17ns 骤降到 3.37ns（**提速 +45.4%**）。
- **致命盲区**：开发者误以为大获全胜，匆匆向开源上游提交了 PR。

### 阶段 2：现实当头棒喝与“宏观崩盘”
- **维护者 Nathan 指出硬伤**：在 16~47 字节中短失配区间，单独对一个 16 字节块调用 `vmaxvq_u8` 会引入巨大的规约时延；
- **宏观负载实测**：在 `deflate_bench` 综合测试中，`mixed` 复合数据在 Level 9 下吞吐直接**暴跌 +13.5%**！
- **质问**：*“After making the change please post new benchmarks... Are you human?”*

### 阶段 3：深入微架构物理确界（第一性原理分析）

```
                     ┌───────────────────────────────┐
                     │   GPR 整数执行域 (x0-x30)     │
                     │  ALU (1c) / Load-to-Use (3c)  │
                     └──────────────┬────────────────┘
                                    │
                                    │ 跨域搬移 fmov (2~3 周期时延)
                                    ▼
                     ┌───────────────────────────────┐
                     │   FPR/NEON 向量域 (v0-v31)    │
                     │  veorq (1c) / vmaxvq (3~4c)   │
                     └───────────────────────────────┘
```

1. **GPR vs FPR 物理跨域时延**：
   - 整数寄存器（GPR）和向量寄存器（FPR）位于不同的物理寄存器文件（PRF）中。
   - 把向量寄存器中的车道数据提取到整数寄存器（`fmov x0, d0`）需要跨越专用旁路总线，带来 **2~3 个周期的固定延迟**。
2. **LZ77 算法的真实语料分布特征**：
   - **>90% 的匹配尝试在最初 8~16 字节内就会发生失配**（哈希假冲突或字面量）。
   - 如果一上来就发射向量加载与跨域搬移，90% 的短匹配都会被这 2~3 个周期的跨域时延拖累，累积起来导致宏观吞吐暴跌！
3. **`vmaxvq` 规约树的时延物理硬伤**：
   - `vmaxvq_u8` 内部是一个 16 字节到 1 字节的 4 级二叉比较树，固定延迟 **3~4 周期且不可流水化**。
   - 只有在 32 字节双展开循环中，这 3~4 周期才能被摊薄到 0.09 周期/字节。

### 阶段 4：体系破局与 Plan B 混合流水线

在彻底搞懂微架构物理机理后，我们重构了分层混合流水线：

```
[0..15B] 纯标量 64-bit GPR (zng_memread_8 ^) ──> 零跨域时延! (拦截 90% 短失配)
    │
    ▼ (若前 16 字节全等)
[16..47B] Nathan 车道标量提取 (vgetq_lane_u64) ──> 避免 solo vmaxvq 规约时延!
    │
    ▼ (若前 48 字节全等)
[48..239B] 2x 双展开 NEON 循环 (vorrq + vmaxvq) ──> 均摊规约开销, 吞吐翻倍!
    │
    ▼
[240..256B] 尾部安全收尾
```

## 3. 核心实验数据对比

通过 5 轮双向交错测试取中位数（变异系数 CV = 1.05%），实测结果表明：
- **微观全长度单调加速**：全 13 个匹配长度耗时降低 **-8.4% 至 -45.4%**；
- **宏观回退彻底消除**：此前 `mixed` L9 的 +13.5% 回退被彻底抹平（恢复至基线 0.0%）；
- **极速层与长匹配大幅提速**：`text` L1 提速 **-18.8%**（128KB）与 **-12.2%**（1MB），`striped_rgb` 全线提速 **-4.7% 至 -6.5%**。

## 4. 开源协作反思与工程伦理

1. **工具与人的关系**：
   AI 可以极快地生成代码和图表，但 AI 无法替代对硬件物理机理的敬畏。没有深入汇编指令流和微架构发射端口的“Vibe Coding”，只会产出看似合逻辑实则性能倒退的劣质补丁。
2. **开源信任的建立**：
   开源维护者对代码的严苛，是守护全球工业软件稳定性的底线。面对质疑，最好的回应不是辩解，而是**彻底认错的谦逊 + 详尽的物理分析 + 100% 严密的消融实验数据**。
