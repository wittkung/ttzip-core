## 2. 各算法开源实现深度技术审视与客观权衡

> **审视原则**：摒弃空泛结论，全面剖析每个开源库在**单核指令级优化**、**多核分块调度**、**流式处理限制（Streaming vs Buffer）**、**内存驻留开销（Memory Footprint）**与**开源许可证边界**上的实际表现与客观权衡。

### 2.1 Deflate (RFC 1951 / GZIP / ZIP)

| 维度 | 单核最优实现：[`ebiggers/libdeflate`](https://github.com/ebiggers/libdeflate) | 多核调度参考：[`madler/pigz`](https://github.com/madler/pigz) | 标准兼容参考：[`zlib-ng/zlib-ng`](https://github.com/zlib-ng/zlib-ng) |
| :--- | :--- | :--- | :--- |
| **开源协议** | **MIT** | **zlib License** | **zlib License** |
| **单核微架构** | • 平铺缓存行哈希表（100% 驻留 L1 D-Cache）<br>• SWAR 64位无损字比对 + ARM64 NEON / x86 AVX2 向量匹配<br>• 11~12 位直接查表型典范哈夫曼解码器（`fast_loop` 无分支直出） | — | • 现代重构版 zlib，全平台 SIMD 优化（SSE/AVX/NEON）<br>• 完整保留 `deflateInit2/deflate/deflateEnd` 标准流式状态机 |
| **多核架构** | — | • Master-Worker 队列，按 128KB~1MB 分块<br>• 32KB 滑窗字典预热传递 (`deflateSetDictionary`) | — |
| **实测性能** | 单核压缩 60~350 MB/s，单核解压 1.2~2.2 GB/s | 16核整机吞吐 3.5~4.5 GB/s | 单核压缩 40~180 MB/s，解压 600~1,100 MB/s |

#### ⚠️ 客观技术权衡与限制：
1. **`libdeflate` 不支持任意流式追加（Non-Streaming API）**：
   * `libdeflate` 专为“已知大小的全内存块”设计，内部不维护传统 zlib 那种任意小片段输入输出的悬挂流式状态机。
   * **工程应对**：针对大文件必须在 C 层构建固定分块缓冲区（如 TTZip 实现的 1MB 环形队列 `ZipChunkedStream`），将流切为整块喂给 `libdeflate`；若遇到无法预知分块的纯流式管道，需备选 `zlib-ng`。
2. **多核位流拼接合规性**：
   * GZIP 多核输出应优先采用 RFC 1952 多成员模式；ZIP 则走文件级并发，完全消除跨块位流移位开销。

### 2.2 Zstandard (RFC 8878)

| 维度 | 官方实现：[`facebook/zstd`](https://github.com/facebook/zstd) (Yann Collet / Meta) |
| :--- | :--- |
| **开源协议** | **BSD 3-Clause / GPLv2 双协议** |
| **单核微架构** | • 有限状态熵 (tANS / FSE)：单状态整数表跳转，完全消除除法指令<br>• 4 流交织超标量哈夫曼：字面量单核解压 >3.5 GB/s<br>• 多级匹配器：Double-Fast (双哈希)、BT-Lazy2 (二叉树)、LDM (最高 2GB 远程滑窗) |
| **多核架构** | • 库级原生多线程 (`ZSTD_compressStream2` 传入 `nbWorkers > 0`)<br>• 无锁任务环形队列 (`ZSTD_JobQueue`)，自动按 `jobSize` (典型 2~8MB) 切片<br>• `overlapLog` 机制自动传递前一 Job 滑动窗口哈希表 |
| **实测性能** | 单核压缩 15~600 MB/s，单核解压 2.5~5.0 GB/s；多核（16核）整机压缩 6~10 GB/s |

#### ⚠️ 客观技术权衡与限制：
1. **高压缩级别与 LDM 的内存爆炸风险**：
   * 在 Level 19 配合 Long Distance Matching (LDM) 时，若开启 16 线程，每个 Worker 分配独立的大窗口哈希表，整机内存可能飙升至 **> 16GB**。
   * **工程应对**：必须在 `TTZipArchiveConfig` 中对多核模式下的单个 Job 窗口施加严格的内存预算上限（如限制每线程最大 64MB~128MB），防止小内存机器发生 OOM。

### 2.3 LZMA / LZMA2

| 维度 | 官方标准：[`tukaani-project/xz`](https://github.com/tukaani-project/xz) (`liblzma`) | 极致提速：[`conor42/fast-lzma2`](https://github.com/conor42/fast-lzma2) |
| :--- | :--- | :--- |
| **开源协议** | **Public Domain / LGPL-2.1+** | **BSD 3-Clause** |
| **单核微架构** | • 11 位定点二进制算术区间编码器 (11-bit BARC) + 12 状态马尔可夫链<br>• 传统二叉树/哈希链匹配器 (BT4) | • **基数树匹配查找器 (Radix Match Finder)**：消除二叉树指针追逐<br>• 分支预测优化区间编码循环 |
| **多核架构** | • 传统按块切分，单线程解压 | • 深度利用 LZMA2 控制字节（`0x01` 状态重置 / `0x02` 字典重置）<br>• 多线程 Job 队列并行分块 Radix 匹配与区间编码 |
| **实测性能** | 单核压缩 8~15 MB/s (慢) | 单核压缩 **25~45 MB/s** (较 liblzma **提速 2.5x~3.5x**) |

#### ⚠️ 客观技术权衡与限制：
1. **压缩比与速度的微小权衡**：
   * `fast-lzma2` 的 Radix 匹配查找器极大提升了搜索速度，但在个别极端数据集（如高度重复的特定二进制代码）上，极限压缩比可能比 Igor Pavlov 原版慢速 BT4 少 0.5%~1.0%。
   * **工程应对**：普通模式与极速模式默认采用 `fast-lzma2`（换取 3.5 倍时间缩短）；如果用户显式勾选“极限冷存储/不计耗时”，可切回标准 7-Zip LZMA2 BT4 引擎。

### 2.4 LZ4 / LZ4-HC

| 维度 | 官方标准：[`lz4/lz4`](https://github.com/lz4/lz4) (Yann Collet) |
| :--- | :--- |
| **开源协议** | **BSD 2-Clause** |
| **单核微架构** | • 纯字节对齐 Token (高 4 位字面量长度，低 4 位匹配长度)，零熵编码<br>• SWAR 与 SIMD 128 位无分支内存直拷 (`LZ4_wildCopy64`/`wildCopy32`)<br>• 单项哈希表碰撞直接覆盖，消除链表开销 |
| **多核架构** | • LZ4 Frame 标准独立块模式 (`LZ4F_blockIndependent`)<br>• 64KB ~ 4MB 独立块无状态并发分发，零跨线程锁同步 |
| **实测性能** | 单核解压 **4.5 ~ 7.5 GB/s** (直接打满单核内存总线带宽)；多核整机吞吐超 **25+ GB/s** |

#### ⚠️ 客观技术权衡与限制：
1. **压缩比极低**：
   * LZ4 专为极速设计，压缩比通常仅在 1.5x~2.5x 之间，远低于 Deflate 和 Zstd。
   * **工程定位**：不可作为通用长久归档格式的主力，仅作为系统临时中转、实时预览快速解压与进程间 IPC 传输的核心引擎。

### 2.5 BZIP2 / Burrows-Wheeler 变换

| 维度 | 传统实现：[`libbzip2`](https://sourceware.org/bzip2/) + [`libdivsufsort`](https://github.com/y-256/libdivsufsort) | 多核参考：[`kjn/lbzip2`](https://github.com/kjn/lbzip2) |
| :--- | :--- | :--- |
| **开源协议** | **BSD-like + MIT** (100% 商业合规) | **GPL-3.0** (🚨 存在许可证传染风险) |
| **单核微架构** | • 采用 MIT 协议的 `libdivsufsort` 诱导排序后缀数组（BWT），彻底解决原版快排在长重复模式下的 $O(N^2)$ 退化问题 | • 类似 DivSufSort 的 BWT 块排序 |
| **多核架构** | • 基于自研 C 线程池分块并发 | • 900KB 独立块并发<br>• **48位特征位扫描解压** (`0x314159265359` 幻数流定位) |

#### ⚠️ 客观技术权衡与限制：
1. **许可证红线**：
   * `lbzip2` 采用 GPL-3 协议，若直接静态编译进入商业闭源或源码可用软件，会导致整个工程被传染。
   * **工程解法**：采用 `libbzip2` + `libdivsufsort` (MIT) 组合重构单核，在 C 层自研 48 位特征扫描器实现多核解压，既获得同等性能又保证 100% 许可证合规。

### 2.6 专用与小众算法客观审视 (Brotli, LZFSE, Snappy, PPMd, Zopfli, WIM)

| 算法 | 推荐开源仓库 | 协议 | 适用场景 | 关键技术陷阱与局限性 |
| :--- | :--- | :--- | :--- | :--- |
| **Brotli** | `google/brotli` | MIT | Web 前端静态资源、Wasm 包、文本配置 | **质量 11 压缩极慢**：Quality 11 耗时呈指数级上升，日常压缩建议使用 Quality 6~9。 |
| **LZFSE** | `lzfse/lzfse` | BSD-3 | macOS/iOS 跨平台解压兼容 | **非 Apple 平台无硬件优势**：在 Windows 上性能与压缩比均不及 Zstandard L1，仅用于兼容解压苹果生态生成的归档。 |
| **Snappy** | `google/snappy` | BSD-3 | 数据库持久化、低延迟流式通信 | **原生无完整 Framing**：核心仅提供 Buffer API，跨平台文件流需要额外的 Framing 头格式。 |
| **PPMd** | 7-Zip LZMA SDK | Public Domain | 纯文本、XML/JSON 结构化大文件 | **内存极度敏感且不可随机访问**：Order-$k$ 状态机在复杂数据上容易引发 SubAlloc 内存耗尽。 |
| **Zopfli** | `google/zopfli` | Apache-2.0 | 静态发布包发布前一次性终极压缩 | **极度耗时（0.5~2 MB/s）**：仅用于发布包构建流程，不可用于桌面客户端实时交互压缩。 |
| **LZX/XPRESS** | `ebiggers/wimlib` | LGPL-3 | Windows WIM/ESD 镜像解析与制作 | **LGPL-3 边界隔离**：需作为独立动态库或独立 C 模块进行清晰边界隔离。 |
| **Blosc2** | `Blosc/c-blosc2` | BSD-3 | 科学计算、遥感气象、AI 浮点张量 | **需前置数据类型感知**：必须知晓元素宽度（4字节 float / 8字节 double）才能进行有效 Byte-Shuffle。 |
