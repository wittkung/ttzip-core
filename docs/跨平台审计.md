## 1. 根本问题诊断

### 1.1 Swift 层承载了过多引擎核心逻辑

当前 Swift 层（68,700 行）不仅包含 GUI 表现层，还包含：

- **归档编排逻辑**：`ArchiveWriter`, `ArchiveExtractor`, `ArchiveReader` 负责"遍历文件 → 压缩 → 写入头部 → 封口"的完整流程
- **容器格式拼装**：`Zip/`, `SevenZip/`, `Tar/`, `Zstd/`, `Brotli/`, `Snappy/` 等格式目录包含大量元数据拼装与流分发逻辑
- **并行调度策略**：`ConcurrencyPatterns/`, `Adaptive/`, `Pipeline/` 包含基于 Swift `async/await` 和 `TaskGroup` 的并发架构
- **基准测试框架**：`Benchmark/` 大量使用 Foundation `ProcessInfo`, `FileManager`
- **安全与校验**：`Crypto/`, `Security/` 包含密钥管理与校验逻辑

**这些都是引擎核心功能，不是 GUI 功能。** 它们绑定在 Swift 层意味着：
- Windows 上无法使用（Swift on Windows 对 Foundation 支持不完整）
- Linux 上需要完整 Swift 运行时（增加 ~200MB 部署体积）
- 无法被 C/C++/C#/Rust/Go 等其他语言直接调用

### 1.2 C 层的并行调度绑定了 Apple GCD

8 个核心 C 文件直接调用 `dispatch_queue_create`, `dispatch_group_async` 等 Apple GCD API。GCD 在 Windows 上不可用（没有官方 `libdispatch` Windows 端口），这意味着整个并行压缩管线在 Windows 上无法编译。

### 1.3 硬件加速代码缺少 x86_64 对等实现

- `ttzip_crc64_pmull.c`：纯 ARM64 PMULL 实现，无 x86 `PCLMULQDQ` 等效路径
- `CTTZipAdler32Neon.c`：纯 ARM NEON `vdotq_u32`，无 x86 `vpmaddubsw` 等效路径
- `CTTZipCRC32Neon.c`：纯 ARM ACLE CRC32，无 x86 SSE4.2 `_mm_crc32_u32` 等效路径

在 Windows x86_64 或 Intel Mac 上，这些关键热路径会退化到纯标量，直接丧失数十倍性能优势。

## 4. 关键设计决策与问题审视

### 4.1 线程池：必须替换 GCD

| 方案 | 优势 | 劣势 | 判定 |
| :--- | :--- | :--- | :--- |
| Apple GCD (`libdispatch`) | macOS 原生，已在用 | **Windows 不可用**，Linux 行为不完全一致 | ❌ 排除 |
| 自研 C11 线程池 | 零依赖，完全可控 | 需要自行处理 Work-Stealing 等复杂调度 | ✅ **选定** |
| C11 `<threads.h>` | C 标准 | MSVC 不完整支持 | ❌ 排除 |
| OpenMP | 简单并行 for 循环 | 不适合异步流式管道 | ❌ 排除 |

**决策**：自研轻量级 C 线程池 (`ttzip_threadpool.c`)。底层用 `pthread_create` (POSIX) 和 `_beginthreadex` / `CreateThread` (Win32)，对上层暴露统一的 `ttzip_threadpool_submit(pool, fn, arg)` 接口。这是 `zstd` 和 `fast-lzma2` 采用的相同模式（二者内部均自研了跨平台线程抽象，而非依赖 GCD）。

### 4.2 硬件加速：必须双 ISA 运行时分发

当前 CRC64/CRC32/Adler32 只有 ARM64 路径。世界级引擎必须做到：

```c
// ttzip_cpu_detect.c
static uint32_t ttzip_cpu_features = 0;

void ttzip_detect_cpu_features(void) {
#if defined(__x86_64__) || defined(_M_X64)
    // x86 cpuid 检测 SSE4.2, AVX2, AVX-512, PCLMULQDQ, AES-NI
    uint32_t eax, ebx, ecx, edx;
    __cpuid(1, eax, ebx, ecx, edx);
    if (ecx & (1 << 20)) ttzip_cpu_features |= TTZIP_CPU_SSE42;
    if (ecx & (1 << 1))  ttzip_cpu_features |= TTZIP_CPU_PCLMUL;
    if (ecx & (1 << 25)) ttzip_cpu_features |= TTZIP_CPU_AESNI;
    // ...AVX2/AVX-512 via cpuid leaf 7
#elif defined(__aarch64__) || defined(_M_ARM64)
    // ARM: getauxval(AT_HWCAP) on Linux, IsProcessorFeaturePresent on Windows ARM
    // macOS: 所有 Apple Silicon 均支持 NEON + PMULL + CRC + AES
    ttzip_cpu_features |= TTZIP_CPU_NEON | TTZIP_CPU_PMULL | TTZIP_CPU_CRC32 | TTZIP_CPU_AES;
#endif
}

// ttzip_crc64.c — 运行时分发
uint64_t ttzip_crc64(const uint8_t* buf, size_t len, uint64_t crc) {
#if defined(__aarch64__)
    if (ttzip_cpu_features & TTZIP_CPU_PMULL)
        return ttzip_crc64_pmull(buf, len, crc);   // 48 GB/s
#elif defined(__x86_64__)
    if (ttzip_cpu_features & TTZIP_CPU_PCLMUL)
        return ttzip_crc64_pclmul(buf, len, crc);  // 40+ GB/s
#endif
    return ttzip_crc64_scalar(buf, len, crc);       // 1.4 GB/s 回退
}
```

**缺失的 x86 实现清单**（必须补齐）：

| 算法 | ARM64 实现 (已有) | x86_64 实现 (需新增) | 目标指令 |
| :--- | :--- | :--- | :--- |
| CRC64 | `vmull_p64` 4路折叠 | `_mm_clmulepi64_si128` 4路折叠 | PCLMULQDQ |
| CRC32 | `__crc32d` 12路折叠 | `_mm_crc32_u64` 12路折叠 | SSE4.2 CRC32 |
| Adler-32 | `vdotq_u32` 延迟求模 | `_mm256_maddubs_epi16` 延迟求模 | AVX2 |
| AES-256 | `vaeseq_u8` 8路交织 | `_mm_aesenc_si128` 8路交织 | AES-NI |

### 4.3 文件系统抽象：统一接口，平台专属实现

```c
// ttzip_fs.h — 统一文件系统抽象
typedef struct ttzip_dir_iterator ttzip_dir_iterator_t;

ttzip_dir_iterator_t* ttzip_fs_opendir(const char* utf8_path);

```

**平台实现差异**：

| 操作 | POSIX (macOS/Linux) | Win32 |
| :--- | :--- | :--- |
| 目录遍历 | `opendir` / `readdir` | `FindFirstFileW` / `FindNextFileW` (支持长路径 `\\?\`) |
| 文件元数据 | `lstat` (支持 symlink) | `GetFileAttributesExW` |
| 内存映射 | `mmap` + `MADV_WILLNEED` | `CreateFileMappingW` + `MapViewOfFile` |
| 路径编码 | UTF-8 原生 | UTF-8 → UTF-16 (`MultiByteToWideChar`) |
| 长路径 | 无限制 | 需要 `\\?\` 前缀 (已有 `TTZIP_WIN_LONG_PATH_PREFIX`) |

### 4.4 许可证风险审计

| 库 | 许可证 | 可否静态链入商业软件 | 风险 |
| :--- | :--- | :--- | :--- |
| `libdeflate` | MIT | ✅ 无限制 | 无 |
| `fast-lzma2` | BSD-3 | ✅ 无限制 | 无 |
| `libzstd` | BSD-3 / GPL-2 双协议 | ✅ 选 BSD-3 | 无 |
| `liblz4` | BSD-2 (库) / GPL-2 (CLI) | ✅ 选 BSD-2 | 无 |
| `google/brotli` | MIT | ✅ 无限制 | 无 |
| `lzfse/lzfse` | BSD-3 | ✅ 无限制 | 无 |
| `google/snappy` | BSD-3 | ✅ 无限制 | 无 |
| `libbzip2` (原版) | BSD-like | ✅ 无限制 | 无 |
| **`kjn/lbzip2`** | **GPL-3** | ❌ **不可** | **🚨 传染风险** |
| `ebiggers/wimlib` | LGPL-3 (库) / GPL-3 (CLI) | ⚠️ 仅动态链接 | 静态链接时传染 |
| `libarchive` | BSD-2 | ✅ 无限制 | 无 |
| `Blosc/c-blosc2` | BSD-3 | ✅ 无限制 | 无 |
| `Cyan4973/xxHash` | BSD-2 | ✅ 无限制 | 无 |
| `google/zopfli` | Apache-2.0 | ✅ 无限制 | 无 |

**结论**：
- `lbzip2` 的 GPL-3 许可证是**不可逾越的法律红线**。不能使用其代码。替代方案：使用标准 `libbzip2`（BSD-like）+ 将 DivSufSort 后缀排序算法（MIT 许可证的 `libdivsufsort`）作为独立优化整合。
- `wimlib` 的 LGPL-3 需要动态链接，或使用 `libarchive` 的 WIM 支持替代。

### 4.5 Deflate 并行位流拼接的真实复杂度

之前的方案将多核 Deflate 描述为"中间块设 BFINAL=0，末块设 BFINAL=1"。这过于简化了：

**真实物理约束**：Deflate 块是 **bit-aligned**（位对齐），不是字节对齐。Thread A 输出的 Deflate 块可能结束在某字节的第 5 个 bit。Thread B 的块需要从第 5 个 bit 开始拼接。这意味着：

| 方案 | 描述 | 可行性 |
| :--- | :--- | :--- |
| **方案 A: 字节填充** | 每个 Chunk 末尾填充 0 bits 到字节边界 | ✅ 但浪费 0~7 bits/块，需要空块分隔 |
| **方案 B: 位级移位拼接** | Sequencer 将后续块的全部 bits 左移拼接 | ❌ O(N) 全量移位，性能不可接受 |
| **方案 C: GZIP 多成员** | 每个 Chunk 是独立的完整 GZIP Member（RFC 1952 允许） | ✅ **推荐**。标准合规，`gunzip` 正确处理，`/usr/bin/tar -xzf` 兼容 |
| **方案 D: ZIP 逐文件并行** | ZIP 中每个文件的 Deflate 流是独立的，直接按文件并行 | ✅ **ZIP 格式最优解**。完全绕过单文件内分块的位流协议复杂度 |

**CTO 决策**：
- **ZIP**：按文件级并行（每个文件独立 Deflate 流），完全消除位流拼接问题
- **GZIP/TAR.GZ**：按 RFC 1952 多成员方案，每个 Chunk 输出独立 GZIP Member

## 5. 迁移路径与阶段规划

### Phase 0: C 层补全与解耦 (不破坏现有功能)
1. **新增 x86_64 SIMD 对等实现**：CRC64 PCLMULQDQ、CRC32 SSE4.2、Adler32 AVX2、AES-NI
2. **新增运行时 CPU 特征检测**：`ttzip_cpu_detect.c`
3. **将 GCD `dispatch_*` 替换为自研跨平台线程池**：`ttzip_threadpool.c`
4. **新增跨平台文件系统抽象**：`ttzip_fs_posix.c` + `ttzip_fs_win32.c`

### Phase 1: 容器封装逻辑下沉
5. **将 Swift `Zip/` 目录的元数据拼装逻辑迁移至 `ttzip_zip.c`**
6. **将 Swift `SevenZip/` 目录的固实块/Coders DAG 逻辑迁移至 `ttzip_7z.c`**
7. **将 Swift `Tar/` 目录的 PAX 流式逻辑迁移至 `ttzip_tar.c`**

### Phase 2: 归档编排 API 下沉
8. **将 `ArchiveWriter.createArchive` 的核心编排逻辑迁移至 `ttzip_archive.c`**
9. **将 `ArchiveExtractor` 的核心提取逻辑迁移至 `ttzip_archive.c`**
10. **定义稳定版本化 C API (`ttzip_api.h`)**

### Phase 3: Swift 层瘦身为纯 GUI 壳
11. **Swift `TTZipCore` 缩减为 `libttzip.a` 的 Swift 绑定薄壳**
12. **将 Swift `Adapters/` 的 C 桥接适配器替换为直接 `@_silgen_name` 或 C Header import**
13. **所有核心逻辑从 Swift `import Foundation` 改为通过 C API 调用**

### Phase 4: Windows 端口
14. **CMake 构建 `ttzip.dll`**
15. **开发 Windows GUI 壳**（C++ WinUI 3 或 C# WPF + P/Invoke）
16. **Windows ARM64 NEON 测试与优化**

| 单核底座 | 自研 LZMA SDK（标量） | 自研（标量） | **SOTA 开源最优引擎集成** |
| 多核调度 | 自研线程池 | 自研线程池 | **自研 C11 线程池 + 字典预热** |
| SIMD 加速 | 部分 SSE2 | 无 | **ARM64 NEON + x86 AVX2 双 ISA 全覆盖** |
| 硬件校验 | 标量 CRC32 | 标量 CRC32 | **PMULL/PCLMULQDQ 向量 CRC64/CRC32 (48+ GB/s)** |
| GUI 解耦 | 紧耦合 MFC | 紧耦合 Windows | **C API 完全解耦，平台 GUI 独立** |

---

## 7. 核心结论

1. **引擎核心必须是一个独立的 Pure C 库**（`libttzip`），零 Swift、零 GCD、零 Foundation 依赖。这是跨平台的物理先决条件，也是世界级压缩软件的工业标准做法。

2. **Swift 层保留为 macOS GUI 的薄壳**（约 5,000~8,000 行），仅负责 SwiftUI/AppKit 渲染、拖拽交互和系统集成，所有压缩/解压/格式处理调用 `libttzip` 的 C API。

3. **硬件加速必须双 ISA**。缺少 x86_64 PCLMULQDQ/SSE4.2/AVX2 路径意味着在 Intel Mac 和 Windows x86 上丧失数十倍性能优势，无法称为世界级。

4. **GCD 必须替换为自研跨平台线程池**。这不是可选优化，而是 Windows 端口的硬性前置条件。

5. **lbzip2 (GPL-3) 不可使用**。替代方案是 `libbzip2` (BSD) + 独立的 MIT 协议 `libdivsufsort` 后缀排序优化。
