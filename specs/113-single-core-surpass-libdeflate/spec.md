## User Scenarios & Testing *(mandatory)*

### User Story 1 - Single-Core Ultra-High-Throughput Compression (Priority: P1)

As a developer or system integrator utilizing TTZip's core archive and compression engine, I want single-threaded DEFLATE compression to execute at significantly higher throughput than existing standard C libraries (such as libdeflate and zlib-ng) across standard benchmarks and real-world payloads, while maintaining full RFC 1951 compliance and zero compression ratio regression.

**Why this priority**: Single-core compression speed defines the baseline efficiency of all archive creation workflows and sets the per-core throughput ceiling for multi-threaded scale-up.

**Independent Test**: Can be tested independently by compressing standard corpora (e.g., Silesia, Enwik8, Canterbury, and mixed binary assets) using a single CPU core and verifying that throughput exceeds libdeflate Level 1 and Level 6 baselines while generating valid, standard-compliant compressed streams.

**Acceptance Scenarios**:
1. **Given** uncompressed input data (10MB to 100MB), **When** compressing in single-core mode at fast levels (Level 1), **Then** compression throughput exceeds libdeflate Level 1 by at least 10% on identical hardware, producing 100% RFC 1951 compliant DEFLATE streams.
2. **Given** structured binary and text data, **When** compressing at balanced levels (Level 6), **Then** compression throughput exceeds libdeflate Level 6 while achieving equal or better compression ratio.
3. **Given** incompressible or high-entropy data (e.g., encrypted or pre-compressed payloads), **When** compression is requested, **Then** the engine rapidly detects entropy and achieves near-memory-bandwidth bypass throughput without CPU stalling.

---

### User Story 2 - Single-Core Ultra-Fast Decompression (Priority: P2)

As an application user extracting archives or processing compressed assets in a single-threaded pipeline, I want single-core DEFLATE decompression to achieve industry-leading extraction throughput that surpasses libdeflate's single-core extraction performance, ensuring instant file extraction with minimal CPU resource consumption.

**Why this priority**: Decompression is a frequent user-facing bottleneck in package installation, asset loading, and archive inspection. Surpassing libdeflate decompression sets a new benchmark for single-core decompression performance.

**Independent Test**: Can be tested independently by decompressing standard DEFLATE streams generated by various standard tools (`gzip`, `zip`, `libdeflate`, `zlib`) on a single core and verifying that single-core extraction throughput exceeds libdeflate extraction throughput by at least 10% to 15%.

**Acceptance Scenarios**:
1. **Given** standard DEFLATE compressed data, **When** decompressing using a single thread, **Then** decompression throughput exceeds libdeflate single-core decompression speed across standard corpora.
2. **Given** streams with small distance matches ($D < 16$) and frequent literal runs, **When** decompressing, **Then** vectorized match replication and multi-symbol literal extraction execute without pipeline stall or branch misprediction.
3. **Given** corrupt or truncated DEFLATE data, **When** decompressing, **Then** the engine safely detects boundaries and returns explicit validation errors without memory corruption, buffer overflow, or crashes.

### User Story 3 - Deterministic Bit-Stream Verification & Cross-Ecosystem Oracle Compatibility (Priority: P3)

As a quality assurance engineer and security auditor, I want all compressed streams generated by the high-performance single-core engine to be bit-exact verifiable and 100% interoperable with all standard ecosystem tools (`/usr/bin/unzip`, `/usr/bin/gzip`, `tar`, standard `libarchive`), ensuring absolute zero regression and zero format lock-in.

**Why this priority**: Extreme speed optimizations must never compromise data integrity or standard compliance.

**Independent Test**: Can be tested independently by round-trip decompressing engine-generated streams with system `/usr/bin/unzip` and `zlib`, verifying byte-exact SHA-256 hash match against original inputs.

**Acceptance Scenarios**:
1. **Given** compressed output from the engine, **When** passed to standard `/usr/bin/gzip -t` or `/usr/bin/unzip -t`, **Then** the verification passes with zero warnings or errors.
2. **Given** arbitrary input files, **When** compressed and decompressed across tool boundaries (Engine -> System Unzip, System Zip -> Engine Decompress), **Then** SHA-256 digests match original inputs 100%.

### Edge Cases

- **Zero-Byte & Micro Payloads (< 64 bytes)**: Engine must handle empty and small inputs with minimal framing overhead and zero memory allocation.
- **Extreme Repetitive Payloads (e.g., 100MB of single byte)**: Match finder and run-length encoders must collapse repetitions at hardware write-bandwidth speed without integer overflow.
- **High-Entropy / Random Payloads**: Early entropy rejection must prevent hash thrashing and avoid expanding data beyond the RFC 1951 uncompressed block boundary limits.
- **Malicious / Truncated Bitstreams**: Decompressor must enforce strictly bounded sliding window boundaries and bit-buffer bounds without reading or writing out of allocated buffers.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Single-core compression engine MUST produce RFC 1951 compliant DEFLATE streams readable by any standard-compliant DEFLATE decompressor.
- **FR-002**: Single-core decompression engine MUST parse and decode all valid RFC 1951 compliant dynamic Huffman, fixed Huffman, and uncompressed blocks.
- **FR-003**: The compression engine MUST implement multi-lane parallel hash probing and SWAR/vectorized match length evaluation to eliminate scalar search bottleneck.
- **FR-004**: The compression engine MUST support dual-token parallel bitstream packing to reduce bitstream emission instruction count.
- **FR-005**: The decompression engine MUST implement dual-symbol simultaneous Huffman decoding for high-frequency short-code literal sequences.
- **FR-006**: The decompression engine MUST implement vectorized small-distance ($D < 16$) match replication without scalar fallback loops.
- **FR-007**: The engine MUST maintain zero intermediate heap allocations on the compression and decompression hot paths, operating exclusively within pre-allocated or stack-bounded scratch buffers.
- **FR-008**: The engine MUST provide continuous single-core throughput monitoring and differential regression testing against libdeflate baselines.

---

### Key Entities

- **Compression Context**: Holds pre-allocated match-finder tables, sliding window scratch buffers, and bitstream emission state.
- **Decompression Context**: Holds pre-allocated Huffman lookup tables (literal/length and distance tables), 64-bit branchless bit-buffer state, and output window cursor.
- **Huffman Table Definition**: Compact lookup tables optimized for single-cycle combined symbol and extra-bit extraction.
- **Benchmark Corpus**: Standard dataset collections (Silesia, Enwik8, mixed media) used for differential throughput and ratio verification.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Single-core compression throughput on Apple Silicon M-series performance cores exceeds libdeflate Level 1 throughput by $\ge 10.0\%$ on Silesia corpus.
- **SC-002**: Single-core balanced compression throughput exceeds libdeflate Level 6 throughput by $\ge 5.0\%$ with equivalent or superior compression ratio.
- **SC-003**: Single-core decompression throughput exceeds libdeflate decompression throughput by $\ge 10.0\%$ across standard corpora.
- **SC-004**: 100% round-trip byte-level verification against standard system decompressors (`/usr/bin/unzip`, `/usr/bin/gzip`, `zlib`) across 1,000+ randomized test corpora.
- **SC-005**: Zero dynamic heap allocations (`malloc`, `posix_memalign`, `Data(count:)`) during active single-core compression/decompression execution.
