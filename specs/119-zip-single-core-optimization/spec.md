## Clarifications

### Session 2026-08-19
- **Q1: Which subsystems are in scope for single-core ZIP optimization?**
  - **Decision**: Full vertical stack optimization, including (1) LZ77 match-finding & SWAR/SIMD comparison, (2) dynamic/canonical Huffman coding & bitstream emission, (3) hardware-accelerated CRC-32 pipelining, (4) single-core streaming Deflate decompression with direct table lookups and vector match expansion, and (5) zero-allocation ZIP container metadata and direct I/O formatting.
- **Q2: How does single-core optimization relate to existing frozen ZIP files?**
  - **Decision**: All architectural enhancements are implemented within the native C engine (`CTTZipBridge/native_deflate`, `CTTZipBridge_ZipWrite*.c`, `CTTZipExtract.c` via approved extension interfaces or dedicated single-core modules), maintaining strict zero-regression across all existing multi-threaded benchmarks.
- **Q3: What are the primary performance targets on Apple Silicon single performance cores (P-cores)?**
  - **Decision**:
    - Level 1 Compression: $\ge 2,200\text{ MB/s}$ (surpassing libdeflate Level 1 by $> 10\%$).
    - Level 6 Compression: $\ge 800\text{ MB/s}$ (surpassing libdeflate Level 6 while maintaining optimal compression ratio).
    - Decompression: $\ge 8,500\text{ MB/s}$ on high-redundancy streams, $\ge 4,800\text{ MB/s}$ on mixed corpus.
    - CRC-32 Checksumming: $\ge 35\text{ GB/s}$ via ARM64 PMULL / CRC32 instruction interleaving.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Single-Core High-Throughput Deflate Compression (Priority: P1)

As an archive creator, CLI user, or background single-threaded compression worker, I want single-core Deflate compression to achieve extreme data throughput across low and balanced compression tiers, so that single-threaded archiving operations complete with minimal latency and maximal CPU energy efficiency.

**Why this priority**: Single-core throughput is the fundamental physical building block of all compression pipelines. A higher single-core throughput directly increases multi-core scaling efficiency and provides immediate performance gains on single-threaded batch workflows, background daemons, and low-power devices.

**Independent Test**: Can be validated via single-threaded microbenchmarks and macro benchmarks on standard corpora (Silesia, Enwik8, Canterbury, and binary payloads), asserting compression throughput and compression ratio across Levels 1 through 6 against libdeflate and zlib-ng baselines.

**Acceptance Scenarios**:
1. **Given** uncompressed input data (1MB to 100MB), **When** compressed in single-core mode at Tier 1 (Fast), **Then** compression throughput reaches $\ge 2,200\text{ MB/s}$ on Apple Silicon P-cores, producing 100% RFC 1951 compliant Deflate streams.
2. **Given** mixed text and binary corpora, **When** compressed at Tier 2 / Level 6 (Balanced), **Then** throughput reaches $\ge 800\text{ MB/s}$ with a compression ratio equal to or better than standard libdeflate Level 6.
3. **Given** incompressible or high-entropy data (e.g. encrypted or pre-compressed assets), **When** compressed, **Then** the match finder executes fast entropy short-circuiting to emit uncompressed blocks at memory-bus speeds ($\ge 6,000\text{ MB/s}$) without CPU pipeline stalling.

---

### User Story 2 - Single-Core Ultra-Fast Deflate Decompression (Priority: P2)

As a user extracting ZIP archives or a developer processing compressed streams in single-threaded pipelines, I want single-core Deflate extraction to achieve industry-leading decoding throughput, so that archives are extracted instantly with minimal CPU overhead.

**Why this priority**: Decompression is an interactive, latency-critical path for software package installation, game asset streaming, and archive browsing. Single-core extraction speed dictates the responsiveness of all extraction tasks.

**Independent Test**: Can be validated by decompressing standard Deflate streams generated by various tools (`gzip`, `zip`, `libdeflate`, `zlib`) on a single core and measuring decode bandwidth and memory access overhead.

**Acceptance Scenarios**:
1. **Given** standard Deflate compressed archives, **When** decompressed on a single thread, **Then** throughput exceeds $\ge 4,800\text{ MB/s}$ on standard corpora and $\ge 8,500\text{ MB/s}$ on highly repetitive streams.
2. **Given** compressed streams containing small match distances ($D < 16$), **When** decompressing, **Then** vectorized small-distance replication copies bytes without falling back to scalar byte-by-byte loops.
3. **Given** streams with sequential short literal runs, **When** decompressing, **Then** multi-symbol simultaneous Huffman decoding extracts consecutive literals in a single table lookup.

---

### User Story 3 - Single-Core Zero-Allocation Container & Checksum Pipelining (Priority: P3)

As a developer creating ZIP archives with thousands of files or large streams, I want ZIP container framing, Local File Header creation, Central Directory generation, and CRC-32 checksum calculation to execute with zero intermediate heap allocations and cache-fused pipelining, so that container overhead consumes $< 2\%$ of total execution time.

**Why this priority**: At gigabyte-per-second compression and decompression speeds, container framing, metadata formatting, and checksum calculation can become significant CPU bottlenecks if not optimized and cache-aligned.

**Independent Test**: Can be validated via single-core ZIP container packing and unpacking benchmarks measuring CPU profiling time spent in framing and CRC32 calculation versus raw Deflate execution.

**Acceptance Scenarios**:
1. **Given** files being compressed or stored into a ZIP archive, **When** computing CRC-32 checksums, **Then** hardware ARM64 PMULL / CRC32 instruction folding processes data at $\ge 35\text{ GB/s}$ when cache-hot, or fuses into the read/write pipeline with zero extra memory passes.
2. **Given** an archive with thousands of small files, **When** writing Local File Headers and Central Directory records, **Then** all header structs are formatted in-place within pre-allocated page buffers with zero per-file heap allocation.
3. **Given** file writing to APFS filesystems, **When** outputting archive data, **Then** APFS extent preallocation and aligned Direct I/O prevent filesystem block allocation stalls.

---

### User Story 4 - Multi-Tier Adaptive Pareto-Optimal Single-Core Strategy (Priority: P4)

As a CLI or GUI user selecting between speed and compression ratio, I want a well-defined spectrum of single-core compression tiers (Store, Fast, Balanced, High, Ultra) where each tier represents a Pareto-optimal trade-off between throughput and compression density without performance cliffs.

**Why this priority**: Users require predictable performance profiles tailored to their specific use cases (e.g. instant backup vs network transfer vs long-term storage).

**Independent Test**: Can be validated by executing a full-matrix benchmark across all defined tiers on standard corpora and plotting the resulting Pareto frontier (throughput vs compression ratio).

**Acceptance Scenarios**:
1. **Given** any standard dataset, **When** evaluated across all 5 single-core tiers, **Then** each successive tier provides a strictly higher compression ratio with mathematically bounded throughput decay.
2. **Given** high-end compression tiers (Levels 9..12), **When** near-optimal Dynamic Programming parsing is active, **Then** graph-search pruning limits single-core execution time to predictable bounds.

---

### Edge Cases

- **Zero-Byte & Micro Payloads (< 64 bytes)**: Framing and header emission must execute in $< 50\text{ ns}$ without allocating dynamic buffers.
- **Extreme Repetition Payloads (e.g. 100MB of uniform bytes)**: LZ77 match finder must collapse repetitions at hardware memory write speeds without 32-bit counter overflow.
- **High-Entropy / Incompressible Payloads (e.g. `.jpg`, `.mp4`, `.enc`)**: Immediate entropy detection within the first 1KB must trigger uncompressed Deflate block (Store) emission to prevent wasted CPU cycles.
- **Corrupt or Malicious Bitstreams**: Decompressor must strictly enforce sliding window boundaries, Huffman tree valid code bounds, and maximum output length guards, failing gracefully with descriptive error codes without memory leaks or segmentation faults.
- **Unaligned Buffer Offsets**: All SIMD and SWAR operations must handle arbitrary source and destination pointer misalignments (0..63 bytes) without bus errors or scalar fallback penalties.

## Requirements *(mandatory)*

### Functional Requirements

#### 1. LZ77 Match Finding & Vector Comparison
- **FR-001**: Single-core compression engine MUST implement L1-cache-resident hash tables (8K..16K entries, $\le 64\text{KB}$) for Fast tiers to ensure zero L2 cache thrashing during match candidate lookups.
- **FR-002**: Engine MUST implement multi-candidate direct-associative hashing (2-way / 4-way per hash bucket) fetching multiple candidate pointers in a single 64-byte cache line access.
- **FR-003**: Engine MUST utilize 64-bit SWAR and 128-bit ARM64 NEON vector comparison (`compare256`) for branchless match length evaluation up to 258 bytes.
- **FR-004**: Engine MUST support adaptive hash skipping and early exit heuristics when high match density or high entropy is detected.

#### 2. Huffman Coding & Bitstream Generation
- **FR-005**: Engine MUST implement branchless 4-way / 8-way parallel symbol frequency histogram generation.
- **FR-006**: Engine MUST implement fast canonical Huffman tree construction with fixed-depth bounds (max 15 bits for literals/lengths, max 7 bits for distances).
- **FR-007**: Engine MUST utilize a 64-bit branchless bit-buffer accumulator with word-at-a-time (32-bit / 64-bit) output flushing.
- **FR-008**: Engine MUST support dual-token simultaneous bit-packing for consecutive literal and match tokens.

#### 3. Deflate Decompression Optimization
- **FR-009**: Decompression engine MUST implement direct primary Huffman lookup tables (10-bit to 12-bit index) capable of resolving $> 99\%$ of literal/length symbols in a single memory lookup without subtable branching.
- **FR-010**: Decompression engine MUST support dual-symbol simultaneous decoding for high-frequency short-code literal pairs.
- **FR-011**: Decompression engine MUST implement vectorized small-distance ($D < 16$) match replication using vector shuffle/duplicate instructions without scalar loops.
- **FR-012**: Decompression engine MUST perform unconditional 16-byte / 32-byte fast vector stores for non-overlapping matches with output buffer padding safety.

#### 4. Container, Checksum & I/O Pipelining
- **FR-013**: Engine MUST implement ARM64 PMULL / CRC32 hardware-accelerated checksumming capable of $\ge 35\text{ GB/s}$ throughput on cache-hot buffers.
- **FR-014**: Checksum computation MUST be pipelined or cache-fused with compression reading / decompression writing to eliminate redundant memory passes.
- **FR-015**: ZIP container framing (Local File Headers, Data Descriptors, Central Directory records) MUST operate with zero dynamic heap allocations on the hot path.
- **FR-016**: File I/O MUST support memory mapping (`mmap` with `posix_madvise`) and APFS extent preallocation for single-threaded streaming writes.

---

### Key Entities

- **Match Finder Context (`ttzip_deflate_mf_t`)**: Holds cache-aligned hash tables, previous link chains, window offset pointers, and entropy statistics.
- **Bitstream State (`ttzip_bitstream_t`)**: 64-bit bit accumulator, bit count, and direct output byte pointer.
- **Huffman Table Spec (`ttzip_huffman_table_t`)**: Pre-allocated primary table (10..12 bit direct mapping) and secondary subtable entries for literal, length, and distance decoding.
- **Checksum State (`ttzip_crc32_state_t`)**: ARM64 CRC32 instruction context with multi-lane PMULL vector folding intermediate registers.
- **ZIP Framing Buffer (`ttzip_zip_frame_t`)**: Pre-allocated page-aligned buffer containing formatted ZIP metadata headers.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: **Single-Core Tier 1 Compression Throughput**: Single-core Level 1 compression achieves $\ge 2,200\text{ MB/s}$ on Apple Silicon P-cores across the Silesia benchmark corpus ($> 10\%$ speedup over standard libdeflate Level 1).
- **SC-002**: **Single-Core Tier 2 (Level 6) Compression Throughput**: Single-core Level 6 compression achieves $\ge 800\text{ MB/s}$ on Apple Silicon P-cores with compression ratio $\le$ baseline compressed size.
- **SC-003**: **Single-Core Decompression Throughput**: Single-core Deflate decompression achieves $\ge 4,800\text{ MB/s}$ on mixed corpus and $\ge 8,500\text{ MB/s}$ on redundant text/binary corpus ($> 10\%$ speedup over libdeflate).
- **SC-004**: **CRC-32 Single-Core Throughput**: Hardware PMULL/CRC32 folding reaches $\ge 35\text{ GB/s}$ on in-cache data and $\ge 15\text{ GB/s}$ on large memory buffers.
- **SC-005**: **Zero Intermediate Allocations**: Hot paths for single-core compression, decompression, and framing perform 0 dynamic `malloc` / `free` calls per file.
- **SC-006**: **Cross-Ecosystem Interoperability & Bit-Exact Correctness**: 100% of generated ZIP archives and Deflate streams pass validation with `/usr/bin/unzip -t`, `/usr/bin/gzip -t`, `tar`, and `libarchive` without error.

## Assumptions

- Target environment is macOS 14.0+ on Apple Silicon (ARM64 with NEON, CRC32, and PMULL extensions), with C11 / POSIX portable scalar fallbacks for x86_64.
- Single-core benchmark measurements are executed on dedicated performance cores (P-cores) under monotonic high-resolution timing.
- Input and output memory buffers for compression and decompression provide at least 64-byte padding at buffer ends to allow safe unaligned vector operations without bounds checking overhead in inner loops.
