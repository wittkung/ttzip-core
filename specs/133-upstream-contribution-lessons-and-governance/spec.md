## 1. Executive Summary & Context

Over the course of developing TTZip and proposing performance optimizations to Tier 2 upstream foundational software (notably `zlib-ng PR #2416`), significant engineering friction and profound lessons emerged:
1. **The Danger of Blind AI-Assisted Submissions**: Submitting optimizations generated by AI without a 100% grounded understanding of low-level machine assembly, microarchitectural register domain crossings (FPR vs GPR), and compiler optimization heuristics damages upstream trust and wastes maintainer bandwidth.
2. **The "Narrow Win / Broad Regression" Trap**: Optimizing for a single isolated microbenchmark length (e.g., 256-byte matches) can introduce subtle yet severe regressions on high-frequency real-world workloads (e.g., short matches, compound text, level 9 deflate on `mixed`), unless validated across a multi-dimensional, multi-workload matrix with rigorous statistical confidence (CV < 1.5%).
3. **Open-Source Respect & Human Communication Discipline**: Foundational software maintainers carry decades of hard-won wisdom regarding platform portability, compiler quirks, and maintenance costs. Communications must be humble, direct, evidence-based, devoid of repetitive AI boilerplate, and respectful of maintainer attention.

This feature formalizes these lessons into TTZip's permanent engineering constitution, automated pre-flight audit toolchains, and educational curriculum materials.

## 2. User Scenarios & Testing *(mandatory)*

### User Story 1 - Automated Upstream Pre-Flight Quality Gate (Priority: P1)

As a core developer or AI assistant proposing a patch to any upstream open-source dependency (e.g., `zlib-ng`, `libdeflate`, `libarchive`, `zstd`), I want an automated pre-flight audit script that executes single-variable ablation tests, multi-workload matrix benchmarks, and microarchitectural assembly diffs before any git push or PR creation, so that zero regressed code or shallow patches are ever submitted to external maintainers.

**Why this priority**: Directly prevents upstream reputational damage and enforces engineering rigor at the physical tooling level.

**Independent Test**:
Can be fully tested by running `python3 scripts/upstream_audit_gate.py` against a candidate branch, verifying that any detected workload regression (> 2%) or missing assembly analysis immediately fails the pre-flight gate with clear actionable diagnostics.

**Acceptance Scenarios**:
1. **Given** a proposed upstream patch modifying an inner loop or SIMD routine, **When** the pre-flight gate is executed, **Then** it automatically runs Google Benchmark across all 8 standard workloads (`text`, `striped_rgb`, `dna`, `mixed`, `short_match`, `random`, `literals`, `realistic_rgb`) across 128KB and 1MB payloads with 5-repetition cooldown medians.
2. **Given** a patch that accelerates a micro-case but causes a regression > 2% on any macro level, **When** the audit tool analyzes the results, **Then** it rejects the patch with a red regression alert pinpointing the exact workload, level, and buffer size.
3. **Given** a patch passing all benchmark floors, **When** the audit tool completes, **Then** it generates a standardized, sorted markdown table and raw JSON artifact ready for clean PR presentation.

### Edge Cases

- **What happens when an upstream maintainer responds with skepticism or asks "Are you human?"**:
  - The protocol dictates immediate cessation of automated phrasing, stepping back to analyze the underlying technical truth, writing an authentic personal reply, and demonstrating deep mechanical understanding via single-variable ablation data.
- **What happens when benchmark results exhibit high variance (CV > 3%) due to thermal throttling or background OS noise**:
  - The audit tool must enforce 5+ interleaved repetitions with thermal cooldown intervals, discarding skewed runs and reporting median values alongside explicit CV distributions.
- **What happens when a patch is rejected due to maintainer preferences for code simplicity or compiler portability**:
  - The protocol requires immediate acceptance of the maintainer's architectural decision without argumentative pushback, offering clean alternatives (e.g. unrolled loops without inline assembly or local helper macros).

## 3. Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST provide an automated pre-flight CLI tool (`scripts/upstream_audit_gate.py`) that benchmarks upstream candidate worktrees against baseline develop branches across all standard Google Benchmark matrices.
- **FR-002**: The pre-flight audit tool MUST compute the Coefficient of Variation ( = \frac{\sigma}{\mu}$) for all test points and alert if median  > 2.0\%$.
- **FR-003**: The pre-flight audit tool MUST enforce a zero-macro-regression rule: any workload showing a statistically significant regression exceeding .0\%$ MUST block the audit gate.
- **FR-004**: System MUST update TTZip's Engineering Constitution (`.specify/memory/constitution.md`) with the "Upstream Open-Source Contribution & Hardware Grounding Protocol".
- **FR-005**: System MUST document the complete AArch64 SIMD & Longest Match case study in `docs/study/case_study_arm64_simd_journey.md`, including assembly disassembly analysis (`otool -tv`), register file domain crossing latency explanations, and benchmark trade-off graphs.
- **FR-006**: System MUST ensure all scripts in `scripts/` comply with TTZip logging discipline (zero bare `print` in core bridge routines, structured output in CLI scripts).
- **FR-007**: System MUST provide a reusable Gist publication helper (`scripts/upstream_report_gen.py`) that exports standardized markdown reports and sanitized JSON telemetry.
- **FR-008**: System MUST integrate the lessons learned into the project's subagent prompt guidelines (`.agents/rules/upstream-contribution.md`) to guide future autonomous research agents.

## 4. Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001 (Tooling Automation)**: 100% of upstream candidate patches can be fully audited (13 micro points, 50 macro points, disassembly extraction) via a single CLI command in under 3 minutes.
- **SC-002 (Statistical Rigor)**: Generated benchmark reports consistently achieve an overall median  \le 1.50\%$ across all standard workloads on Apple Silicon and Linux AArch64 environments.
- **SC-003 (Governance Documentation)**: 100% of upstream contribution rules, 5 Core Constitution Invariants, and 3 Pre-Flight Gates are codified and permanently committed in TTZip repository documentation.
- **SC-004 (Educational Quality)**: The case study in `docs/study/` provides a complete end-to-end pedagogical walkthrough (Problem, Naive Approach, Flaw Analysis, Microarchitectural Solution, Benchmark Data, Reflection) with zero jargon ambiguity.

## 5. Key Entities & Data Model

- **UpstreamAuditResult**:
  - `target_function`: string (e.g. `compare256_neon`)
  - `worktree_path`: string
  - `baseline_branch`: string (e.g. `develop`)
  - `candidate_branch`: string (e.g. `feat-arm64-swar-compare256`)
  - `micro_benchmarks`: Map<Length, MeasurementPair> (ns/call, delta%, status)
  - `macro_benchmarks`: Map<WorkloadKey, MeasurementPair> (duration, delta%, status)
  - `statistical_cv`: SummaryStats (median_cv, mean_cv, max_cv)
  - `gate_passed`: boolean
  - `blocking_reasons`: Array<string>

- **MeasurementPair**:
  - `baseline_median_ns`: float
  - `candidate_median_ns`: float
  - `delta_percentage`: float
  - `is_statistically_significant`: boolean
  - `is_regression`: boolean

## 6. Assumptions

- Testing and benchmarking environment operates on Apple Silicon (M-series) or ARM Neoverse AArch64 hardware with Google Benchmark and CMake available.
- All upstream worktrees are managed under `Vendor/worktrees/`.
- The developer uses authenticated GitHub CLI (`gh`) for remote Gist generation and PR tracking.
